# 태풍 지도 렌더링

기상청 태풍 데이터를 다루는 전 구간(API → 파싱 → 기하 → 렌더)의 규약.
세 영역이 서로의 가정에 의존하므로 한 파일로 유지한다.

- **1부 API와 파싱** — 요청 파라미터, 필드 매핑, 정규화
- **2부 기하 계산** — 반경 원, 예보원 콘, 비대칭 폴리곤
- **3부 렌더링** — 레이어 구성, 스타일, 상태 표시

마커: 🚨 조용히 깨지는 함정 / 🔶 실측 검증 필요 / ✅ 검증 완료

# 1부. API와 파싱

## 엔드포인트

베이스: `https://apihub.kma.go.kr`

| 목적 | 경로 | 핵심 인자 |
|---|---|---|
| 연도별 태풍 목록 | `/api/typ01/url/typ_lst.php` | `YY` |
| 태풍 상세 + 예측 | `/api/typ01/url/typ_data.php` | `YY`, `typ`, `seq`, `mode` |
| 시점 기준 조회 | `/api/typ01/url/typ_now.php` | `tm`, `mode` |
| 영향 태풍 통계 | `/api/typ02/openApi/SfcYearlyInfoService/getTyphoonList` | `year`, `dataType`, `pageNo`, `numOfRows` |

`typ01`은 **현재 진행 중인 태풍만** 제공한다. 종료된 태풍은 조회되지 않는다.
발표 주기는 4·10·16·22시 및 수시. 🔶 이 시각이 KST인지 UTC인지 미확정.

## 요청 규칙

**항상 이렇게 고정한다.**

```
disp=1   # 콤마 구분
help=2   # 헤더/설명 없이 값만
```

- `disp=0`은 고정폭 포트란 포맷이다. 컬럼 폭이 명세에 없으므로 파서를 만들지 않는다. 🚨
- `help=0`/`1`은 주석·설명 라인이 섞인다. 파싱 대상이 아니라 사람이 필드를 확인할 때만 쓴다.

**인자를 생략하지 않는다.** 🚨

| 인자 | 생략 시 | 문제 |
|---|---|---|
| `YY` | 올해 | 연말·연초에 결과가 바뀜 |
| `typ` | 그해 마지막 태풍번호 | 새 태풍 발생 시 다른 태풍을 조회 |
| `seq` | 마지막 발표번호 | 재현 불가, 캐시 키 불안정 |

운영 코드는 셋을 모두 명시한다. 목록 조회로 먼저 확정한 뒤 상세를 조회하는 2단 구조로 간다.

## `mode` 의미

| 값 | 범위 |
|---|---|
| 0 | 분석정보만 |
| 1 | 과거 분석 + 가장 최근 예측 |
| 2 | 가장 최근의 분석 + 예측 |
| 3 | 과거 분석 + 과거 모든 예측 |

전부 `seq` 기준 **과거 자료만** 처리한다. 지도 기본 표시는 `mode=1`,
발표 간 경로 비교는 `mode=3`을 쓴다.

## 파싱 규칙

1. **시각은 전부 UTC.** `YYYYMMDDHHmm` 문자열. 변환은 `lib/time.ts` 한 곳에서만.
   다른 파일에서 `+9`를 직접 더하지 않는다.
2. **결측은 `null`.** 0이나 빈 문자열로 정규화하지 않는다. 🚨
   렌더 단계에서 `null`이면 해당 레이어를 그리지 않는다.
3. **`FT`로 분리.** `analysis[]`와 `forecast[]`를 별도 배열로 만든다. 하나의 배열에
   담고 플래그로 구분하는 방식은 정렬 실수가 나기 쉬우니 피한다.
4. **`(YY, TYP, SEQ)` 단위 그룹핑.** `mode=3`은 여러 발표분이 한 응답에 온다.
   seq를 무시하고 합치면 경로가 꼬인다. 🚨
5. **16방위 변환표**를 통해서만 `DIR`, `ED15`, `ED25`를 각도로 바꾼다.

```ts
const COMPASS_16 = {
  N: 0, NNE: 22.5, NE: 45, ENE: 67.5,
  E: 90, ESE: 112.5, SE: 135, SSE: 157.5,
  S: 180, SSW: 202.5, SW: 225, WSW: 247.5,
  W: 270, WNW: 292.5, NW: 315, NNW: 337.5,
} as const;
```

## 오류 상태 구분 🚨

"진행 중 태풍 없음"과 "조회 실패"를 반드시 다른 상태로 표현한다.
실패를 빈 배열로 삼키면 API 장애가 "태풍 없음"으로 화면에 표시되고, 아무도 눈치채지 못한다.

```ts
type TyphoonResult =
  | { status: 'ok'; typhoons: Typhoon[] }
  | { status: 'none' }        // 정상 응답, 진행 중 태풍 없음
  | { status: 'error'; reason: string };
```

## 인증키

`authKey`는 쿼리스트링으로 전달된다. 따라서 **클라이언트에서 직접 호출할 수 없다.**
Cloudflare Worker에 시크릿으로 두고, 프론트는 Worker의 정규화 JSON만 소비한다.
키를 코드·번들·커밋·로그·에러 메시지에 남기지 않는다.

## 테스트

파서 변경 시 `fixtures/raw/`의 실제 응답 픽스처로 스냅샷 테스트를 돌린다.
새 엣지 케이스(결측 반경, 날짜변경선 통과, 열대저압부 전환)를 만나면 픽스처를 추가한다.

# 2부. 기하 계산

모든 출력은 GeoJSON(EPSG:4326). 계산은 구면 기준으로 하고, 평면 근사를 쓰지 않는다.

## 반경 원 생성

중심 좌표 + km 반경 → 폴리곤. 위도가 높아질수록 경도 1도의 실거리가 줄어들므로
`Δlon = Δlat / cos(lat)` 보정 없이 원을 그리면 **타원이 찌그러진 채로 정상처럼 보인다.** 🚨

```ts
// 정점 수는 72개(5도 간격) 이상. 그보다 적으면 확대 시 각이 보인다.
function circle(center: LngLat, radiusKm: number, steps = 72): Position[]
```

turf의 `circle()`을 쓰는 편이 안전하다. 직접 구현할 경우 반드시 고위도(40°N 이상)에서
원형 유지 여부를 눈으로 확인한다.

## 확률반경 콘 (예보원 포락선)

기상청 화면의 노란 영역은 개별 원의 합집합이 아니라, 연속한 두 원의 **공통 외접선**으로
이어 만든 포락선이다. 단순 union으로 그리면 원 사이가 잘록하게 들어가서 다른 모양이 된다. 🚨

절차:

1. 예측 시각별 `(중심, RAD)` 쌍을 시간순으로 정렬
2. 인접한 원 쌍마다 외접선 접점 4개를 계산
3. 접점을 잇는 사다리꼴 + 양 끝 원의 호(arc)를 결합해 단일 폴리곤 생성
4. 자기교차가 생기면(급격한 방향 전환 시) union으로 정리

현재 위치의 원은 반경이 0이거나 매우 작다. 이 경우 접선 계산이 발산하므로
`radiusKm < 1`이면 점으로 처리하는 분기를 둔다. 🚨

시각적으로는 원 경계선을 점선으로 남기고 콘 내부를 반투명 채움으로 둔다.
레퍼런스 화면과 같은 구조다.

## 비대칭 풍속반경

`RAD15` + `ED15`(예외방향) + `ER15`(예외반경) 구조.
레퍼런스 표기: `250 km[남서 약 120 km]`.

🔶 **해석이 확정되지 않았다.** 두 가지 후보:

- (A) `ED15` 방위 한 점만 `ER15`이고 나머지는 `RAD15` → 부드럽게 보간
- (B) `ED15`를 포함하는 사분면 전체가 `ER15` → 계단형 경계

확정 전까지는 **해석을 선택 가능한 파라미터로** 두고 기본값을 (A)로 한다.
코드에 하나를 박아 넣지 말 것. `PROGRESS.md` 미해결 질문 3번과 연동된다.

(A) 구현 시 방위별 반경을 코사인 가중으로 보간한다.

```
r(θ) = RAD - (RAD - ER) * max(0, cos(θ - θ_exception))^k
```

`k`는 예외 영역의 폭을 결정한다. 기본 `k=2`. 이 식은 근사이며 기상청 원자료의
생성 방식과 일치한다는 보장이 없다. 화면에 "근사 표현"임을 명시한다.

**결측 처리**: `RAD25`가 `null`이면 폭풍반경 레이어 자체를 생성하지 않는다.
반경 0의 폴리곤을 만들면 지도에 점이 찍히고, 그게 "폭풍반경 있음"처럼 보인다. 🚨

## 경도 unwrap

북서태평양 태풍은 날짜변경선을 넘을 수 있다. 경로 좌표가 `179.8 → -179.5`로 바뀌면
LineString이 지도를 가로질러 그어진다. 🚨

```ts
// 이전 점 대비 경도 차가 180을 넘으면 ±360 보정
function unwrapLongitudes(coords: Position[]): Position[]
```

폴리곤(반경 원, 콘)도 같은 문제를 겪는다. 원 생성 시 중심 경도를 기준으로
정점 경도를 연속화한 뒤 GeoJSON에 넣는다.

## 경로 보간

발표는 6~12시간 간격이라 그대로 이으면 각진 절선이 된다.
표시용 곡선은 Catmull-Rom 또는 대권 보간으로 부드럽게 만들되,
**보간점은 시각 라벨이나 팝업의 데이터로 쓰지 않는다.** 보간값은 관측·예보값이 아니다. 🚨

원본 발표점은 별도 Point 소스로 유지하고, 라벨·팝업·정보 패널은 그 소스만 참조한다.

## 기하 검증

기하 함수는 순수 함수로 두고 유닛 테스트를 붙인다. 최소 케이스:

- 적도·중위도·고위도(0°/35°/50°N)에서 반경 원의 실제 거리 오차 < 1%
- 날짜변경선 통과 경로가 단일 방향으로 이어짐
- `RAD25 = null`일 때 폴리곤이 생성되지 않음
- 반경 0 원에서 콘 생성이 예외 없이 통과

# 3부. 렌더링

## 소스 구성

GeoJSON 소스를 역할별로 나눈다. 하나의 소스에 전부 담고 filter로 나누는 방식은
갱신 시 전체 재파싱이 일어나므로 쓰지 않는다.

| 소스 id | 지오메트리 | 내용 |
|---|---|---|
| `typhoon-cone` | Polygon | 70% 확률반경 포락선 |
| `typhoon-radius-25` | Polygon | 폭풍반경 (결측 시 미생성) |
| `typhoon-radius-15` | Polygon | 강풍반경 |
| `typhoon-track-past` | LineString | 분석 경로 |
| `typhoon-track-forecast` | LineString | 예측 경로 |
| `typhoon-points` | Point | 발표 시각별 중심 (원본값만) |

## 레이어 순서

아래에서 위로. 면 → 선 → 점 → 라벨.

```
cone (fill) → radius-15 (fill) → radius-25 (fill)
→ track-past (line) → track-forecast (line, dasharray)
→ points (symbol) → current-position (symbol) → labels
```

베이스맵 라벨 위로 태풍 폴리곤이 올라가면 지명이 가려진다.
`beforeId`로 베이스맵의 라벨 레이어 아래에 면 레이어를 삽입한다.

## 갱신 패턴

시각 변경·발표번호 변경 시 `removeLayer`/`addLayer`를 반복하지 않는다.
레이어는 초기 1회 생성하고, 이후 `getSource(id).setData(geojson)`만 호출한다. 🚨
레이어 재생성은 깜빡임과 메모리 누수를 만든다.

레이어 토글은 `setLayoutProperty(id, 'visibility', 'none' | 'visible')`로 처리한다.

## 스타일 토큰

색은 데이터에만 쓴다. UI 크롬은 무채색.

```
--track-past:      #E8E8EC   (분석 경로, 실선)
--track-forecast:  #E8E8EC   (예측 경로, 점선 [2, 2])
--cone-fill:       #F5E27A   투명도 0.35
--cone-stroke:     #D9C24A   점선
--radius-15:       #F2A65A   투명도 0.18
--radius-25:       #E0635A   투명도 0.22
--current:         #FFFFFF   외곽선 강조
```

강도 구분은 색이 아니라 **심볼 크기와 형태**로 준다. 색만으로 구분하면
색각 이상 사용자가 읽지 못하고, 흑백 인쇄에서도 사라진다.

| 강도 | 심볼 |
|---|---|
| 열대저압부 | 작은 원 (×) |
| 강도 1 (중) | 태풍 심볼 소 |
| 강도 2 (강) | 태풍 심볼 중 |
| 강도 3~4 (매우강/초강력) | 태풍 심볼 대 |

## 분석 / 예측 구분 🚨

시각적 구분이 없으면 사용자가 예측을 관측으로 오독한다. 최소 두 가지 수단을 동시에 쓴다.

- 선: 분석 실선 / 예측 점선
- 심볼: 예측 위치는 외곽선만(fill 없음)
- 라벨: 예측 시각에 `+24h` 같은 리드타임 표기

## 팝업과 정보 패널

팝업에 표시하는 값은 **원본 발표값만** 사용한다. 보간된 경로 좌표를 팝업에 쓰지 않는다.
시각은 KST로 표기하되, 원본이 UTC임을 툴팁 등에 남긴다.

패널에 표시할 항목 (레퍼런스 화면과 동일 순서):
중심위치 / 중심기압 / 최대풍속 / 강풍반경[예외반경] / 폭풍반경[예외반경] / 강도 / 진행방향 / 이동속도

결측 항목은 `-`로 표기한다. 값을 숨기거나 0으로 채우지 않는다.

## 상태 표시

- 로딩 중: 지도는 유지하고 패널만 스켈레톤
- 진행 중 태풍 없음: 명시적 빈 상태 문구
- 조회 실패: 오류 배너 + 마지막 성공 시각. 빈 상태와 반드시 구분 🚨
- 데이터 신선도: 마지막 발표로부터 경과 시간 배지. 일정 시간 초과 시 경고색

## 성능

- 폴리곤 정점 수는 원당 72개 수준. 과도한 세분화는 렌더 비용만 늘린다.
- `mode=3` 다중 발표 비교 시 표시 seq 수를 제한한다(기본 3개).
- 애니메이션 재생은 `requestAnimationFrame` 기반, 프레임당 `setData` 1회 이하.
- `prefers-reduced-motion`이면 자동 재생을 비활성화하고 수동 스크럽만 제공한다.

## 접근성

- 레이어 토글과 타임라인은 키보드로 조작 가능해야 한다.
- 지도 위 정보는 반드시 텍스트 패널에도 존재해야 한다. 지도만으로 전달하지 않는다.
- 포커스 링을 제거하지 않는다.
